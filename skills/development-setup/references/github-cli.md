# GitHub CLIの認証ワークフロー

## 診断

エージェントは、対象のGitHubホストと期待する所有者を特定する。
エージェントは、`gh --version` と必要なサブコマンドの `--help` を確認する。
エージェントは、既存のCLIがPATH外にある場合、既知の実行ファイルを使用できる。
CLIが未導入の場合、エージェントは [公式導入手順](https://github.com/cli/cli#installation) を使う。

エージェントは、既存の認証状態とログイン中のアカウントを確認する。

```bash
gh auth status --hostname github.com --active --no-refresh
gh api --hostname github.com /user --jq .login
```

`--no-refresh` は、対応するCLIでだけ使用する。
エージェントは、未対応のオプションを認証失敗と混同しない。
GitHub CLIは、通常のAPI操作で既存認証を自動更新する場合がある。
エージェントは、診断から新規ログインや追加権限の認証を開始しない。

`GH_TOKEN` などの環境変数は、保存済みの認証より優先される。
エージェントは、環境変数の名前と存在だけを確認する。
エージェントは、管理された環境変数を勝手に解除して別の認証へ切り替えない。
環境変数の権限が不足する場合、利用者は提供元で権限を更新する。

別のアカウントが有効な場合、エージェントは所有者の不一致を報告する。
エージェントは、明示されたアカウント切替の依頼に従って `gh auth switch` を使用する。
エージェントは、修復のために既存アカウントを勝手にログアウトしない。

## 不足権限の整理

エージェントは、利用者の依頼操作に必要な権限だけを追加対象にする。

| 依頼操作 | 権限確認の要点 |
|---|---|
| 非公開リポジトリの取得・更新 | 対象リポジトリへのアクセス。 |
| ユーザー所有の非公開リポジトリ作成 | 所有者としての作成権限。 |
| Actionsワークフローの更新 | Workflowsの更新権限。OAuthでは追加の `workflow` scope。 |
| CI用Secretsの登録 | 登録先リポジトリのSecrets更新権限。 |
| 費用情報の取得 | 使用量APIが要求するアカウント側の権限。 |

GitHub CLIのログイン成功は、すべての操作権限を保証しない。
エージェントは、リポジトリの `push` や `admin` だけでSecrets権限を断定しない。
エージェントは、権限確認だけを目的に不要なリポジトリやIssueを作成しない。
エージェントは、依頼された設定操作の結果から書込権限を確認する。

## 新規認証

エージェントは、既存認証が使える場合、新規ログインを省略する。
エージェントは、利用者がブラウザを操作できる段階で対話セッションを開始する。

```bash
gh auth login --hostname github.com --web --skip-ssh-key
```

エージェントは、ホスト名を利用者の指定に合わせる。
エージェントは、必要な場合だけ `--scopes` で追加権限を指定する。
GitHub CLIは、初回ログインで既定の権限も要求する。
エージェントは、実際に表示される権限を利用者へ説明する。

ワークフロー更新を含む初期導入では、エージェントは次の形式を使用できる。

```bash
gh auth login --hostname github.com --web --skip-ssh-key --scopes repo,workflow
```

既存アカウントでOAuth scopeだけが不足する場合、エージェントは追加認証を使う。

```bash
gh auth refresh --hostname github.com --scopes workflow
```

エージェントは、既存の権限を減らす `--reset-scopes` を通常の復旧で使わない。
エージェントは、Gitの既存のSSH・HTTPS設定を維持する。
`--git-protocol` の指定は、同じホストの他アカウントにも影響する。
したがって、エージェントは認証のためにGitの接続方式を勝手に変更しない。

## ブラウザ操作と期限切れ

公式CLIは、認証URLと一時コードを発行する。
エージェントは、現在の対話プロセスを保持する。
エージェントは、公式CLIが要求するEnter入力などを処理する。
エージェントは、URLとコードを発行直後に利用者へ示す。
エージェントは、利用者の完了通知を入力依頼ツールで受け取る。
エージェントは、待機中も依存しない確認を進める。

コードが期限切れの場合、エージェントは同じコードを再利用しない。
エージェントは、失敗したプロセスを終了してから再発行する。
エージェントは、公式CLIが示していない有効期限を推測しない。

## 完了条件

エージェントは、認証プロセスの正常終了を確認する。
エージェントは、`gh api /user` の所有者を期待値と照合する。
エージェントは、依頼対象へのアクセス結果も確認する。
404の応答は、対象の不存在とアクセス不能のどちらも示し得る。
したがって、エージェントは404だけでリポジトリの新規作成を判断しない。

エージェントは、トークン自体を返す `gh auth token` を診断に使わない。
エージェントは、`gh auth status --show-token` を実行しない。
CIへのトークン登録は、対象と権限を明示した別の工程として扱う。
エージェントは、PC用のGitHub認証をCI用の管理トークンへ勝手に複製しない。

公式資料は、[ログイン](https://cli.github.com/manual/gh_auth_login)と[追加権限](https://cli.github.com/manual/gh_auth_refresh)を参照する。
