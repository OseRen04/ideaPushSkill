# Development Setup

エージェントは、初期セットアップを「診断 → 不足の整理 → 認証 → 登録 → 検証」の順で進める。
利用者は、公式サービスのブラウザ画面で本人認証を行う。
エージェントは、利用者の認証操作を待つ間も、依存しない準備を進める。

## 対象と依頼範囲

| 利用者の依頼 | エージェントが行う工程 |
|---|---|
| 初期セットアップを進めて | 対象プロジェクトに必要な診断・認証・設定・接続確認。 |
| GitHub CLIを認証して | GitHubのアカウントと依頼操作の権限確認。 |
| Codexへログインして | 指定環境のCodexログインとローカル状態の確認。 |
| CI用の認証も設定して | 非公開の登録先を確認した上で、専用認証とSecretsを設定。 |
| 認証が切れた・セットアップを再開して | 現在の状態を再診断し、未完了の工程だけを再開。 |
| 認証状態だけ確認して | 読み取り診断。新規ログイン・権限追加・Secrets登録は行わない。 |
| セットアップ用スキルを作成・修正して | スキルの作成・修正だけ。新しい認証セッションは開始しない。 |

エージェントは、利用者が指定した所有者・ホスト・リポジトリ・実行環境を特定する。
既存の会話や設定で対象が明確な場合、エージェントは同じ内容を再確認しない。
エージェントは、認証依頼の範囲内で工程を継続する。
エージェントは、各工程で同じ実行許可を繰り返し求めない。
アカウント切替や認証情報の外部登録では、既存の依頼範囲を確認する。
依頼範囲に含まれない操作では、エージェントは対象と変更内容を具体的に確認する。

## 1. エージェントが実行環境を診断する

エージェントは、利用可能なシェルと公式CLIを確認する。
CLIが利用できない環境では、エージェントは利用者の端末向け手順を案内する。
スキルは、シェルやGitHub APIの新しい操作権限を提供しない。

エージェントは、次の診断ヘルパーを実行できる。
ヘルパーは、ログイン開始・Secrets更新・モデル呼び出しを行わない。

```bash
python3 <skill-dir>/scripts/check_setup.py --expected-owner OWNER --repository OWNER/REPO
```

`<skill-dir>` は、このスキルの実際のディレクトリへ置き換える。
`OWNER` と `OWNER/REPO` は、利用者が指定した値へ置き換える。
`--expected-owner` は、期待する個人ログイン名を指定する。
組織リポジトリでは、エージェントは組織名を個人ログイン名へ流用しない。
エージェントは、ヘルパーの `--help` で追加引数を確認する。
エージェントは、診断結果の秘密を含まない項目だけを表示する。

## 2. エージェントが不足する工程を示す

エージェントは、利用者が操作する工程と自分が実行する工程を示す。
エージェントは、必要な権限と登録先を示してから認証を開始する。
利用者がブラウザを操作できる段階で、エージェントは認証セッションを開始する。
したがって、エージェントは長時間の準備中に認証コードを放置しない。

エージェントは、次の状態を個別に扱う。

| 工程 | 完了と判定する根拠 |
|---|---|
| GitHub CLI | CLIの正常終了と、対象ホストのログイン中アカウント。 |
| GitHubの操作権限 | 依頼された対象と操作に対する確認結果。未検証の書込権限は明示する。 |
| Codexのローカル認証 | 指定CODEX_HOMEでのログイン結果と認証方式。 |
| CI用Secrets | 対象を明示した登録処理の成功。名前の存在だけでは内容の正しさを断定しない。 |
| CIの実証 | 対象CIでの実行結果。認証成功と更新版の保存成功を区別する。 |
| 運用開始 | 利用者の時間指定・費用条件・企画の開発許可。 |

エージェントは、無関係な工程を「対象外」とする。
エージェントは、取得不能な状態を完了や未登録と断定しない。

## 3. エージェントが必要な認証を進める

- GitHub CLIの認証では、エージェントは [GitHubの手順](references/github-cli.md) を読む。
- Codexの認証では、エージェントは [Codexの手順](references/codex.md) を読む。
- Idea Vault Runnerの初期導入では、エージェントは [Runnerの手順](references/idea-vault-runner.md) も読む。

エージェントは、公式CLIが返した認証URLと一時コードだけを案内する。
エージェントは、コードを発行した直後に利用者へ案内する。
利用者は、公式ブラウザ画面で認証する。エージェントは、認証完了をCLIで再確認する。
利用者の「完了」という返答だけでは、エージェントは工程を完了にしない。

## 4. エージェントが中断と期限切れから再開する

エージェントは、認証セッションごとに対象・プロセス・結果を対応付ける。
認証コードが期限切れの場合、エージェントは失敗したセッションを終了する。
エージェントは、公式CLIから新しいURLとコードを取得する。
エージェントは、新しいコードが旧コードを置き換えると利用者へ伝える。
エージェントは、認証後にアカウントと対象を再確認する。

エージェントは、1回の依頼で期限切れによる再発行を最大2回まで行う。
再発行が続く場合、エージェントは利用者が操作できる時点まで認証工程を保留する。
エージェントは、利用者が操作中のセッションを重複して開始しない。
エージェントは、中断後に再診断し、完了済みの認証をやり直さない。
エージェントは、一時コード・トークン・認証JSONを進捗ファイルへ保存しない。

## 5. エージェントが結果を検証して引き継ぐ

エージェントは、工程ごとに「完了・ユーザー操作待ち・未設定・取得不能・対象外」を報告する。
エージェントは、残る作業の担当者と対象を明記する。
ローカルのログイン成功だけでは、エージェントはCIの認証成功を報告しない。
エージェントは、認証完了だけを理由にジョブ・定期実行・開発許可を有効化しない。
エージェントは、秘密を含まない所有者・登録先・検証結果だけを引き継ぐ。

## 認証情報の扱い

エージェントは、パスワード・PAT・認証JSONを会話への貼り付けで求めない。
エージェントは、公式の認証画面か、公式CLIの安全な入力経路を使う。
エージェントは、パスワード・トークン・認証JSONをログやコマンド引数へ出力しない。
エージェントは、パスワード・トークン・認証JSONをGitやArtifactへ保存しない。
エージェントは、既存認証の内容を表示するコマンドを実行しない。
エージェントは、利用者の通常のIDE認証をCIへ無断で転送しない。
エージェントは、API課金への認証方式の切替を自動で行わない。
