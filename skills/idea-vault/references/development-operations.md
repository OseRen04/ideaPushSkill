# 自動開発の設定と状況確認

## リポジトリと変更範囲

ユーザーの指定と既存の接続設定から、所有者と各リポジトリを特定する。
`OseRen04` は現在の導入先であり、別ユーザーへ固定値として流用しない。

| 対象 | 現在の導入先 | 内容 |
|---|---|---|
| 企画管理 | `OseRen04/idea-vault` | `<id>/` 直下の3文書と時間設定。 |
| 実行管理 | `OseRen04/idea-vault-runner` | 非公開のActions設定・制御プログラム・実行状態。 |
| 開発先 | 実行状態の企画別の参照先 | 非公開の開発ブランチ・Issue・PR。 |

通常の企画保存から実行管理用リポジトリを作成しない。
実行先が未導入の場合、設定済み・稼働中とは報告しない。
初期導入は、実行用コードの `docs/OPERATIONS.md` に従う。
認証を含む初期導入では、利用可能な [Development Setup](../../development-setup/SKILL.md) を使う。
通常の保存・閲覧では、エージェントは新しい認証セッションを開始しない。

## 時間設定

ユーザーの明示的な曜日・時間帯・タイムゾーンを使用する。
時間設定は、企画管理用リポジトリの `settings/development-schedule.yaml` へ保存する。
未指定のタイムゾーンは、既存設定または利用環境から特定する。
最大実行時間は、既存設定を維持する。初回は指定時間帯の長さを上限にする。
同時実行数は1とする。終了5分前は保存処理に充てる。

```yaml
enabled: false
timezone: Asia/Tokyo
schedule:
  days: [MON, TUE, WED, THU, FRI]
  start_time: "02:00"
  end_time: "03:00"
limits:
  max_duration_minutes: 60
  max_concurrent_jobs: 1
```

例の値で、ユーザーの設定を上書きしない。
`enabled: true` は、ユーザーが自動開発の開始を明示した場合だけ設定する。
既存設定の時刻変更だけの依頼では、既存の有効・無効を維持する。
日跨ぎの時間帯は、開始日の曜日に紐付ける。同じ開始・終了時刻は拒否する。
実行用コードは、IANAタイムゾーンとDSTを検証する。

実行用cronの保存先は、実行管理用リポジトリの `.github/workflows/autonomous-development.yml` とする。
cronは開始曜日・開始時刻を使用し、`timezone` にIANA名を指定する。
`enabled: false` の場合、`on.schedule` を削除する。
`workflow_dispatch`、権限、同時実行数、各ステップは保持する。

両リポジトリの最新HEADと対象ファイルを取得する。
変更内容を検証し、企画管理用の設定から保存する。
次に、実行管理用のcronを非強制で更新する。
GitHubの既存連携がWorkflowsの更新に対応しなければ、不足を伝える。
片方だけ成功した場合、未同期の対象を明示する。
同期間の競合では、最新版へ再適用する。再試行は最大2回とする。
停止設定では、企画管理用の `enabled: false` を先に保存する。
制御プログラムは、起動時と実行中に最新の時間設定を検証する。

実行用リポジトリの `RUNNER_ENABLED` は、初期設定と実証の完了後に有効化する。
通常の時間設定から、未確認の認証・費用条件を有効化しない。
時間設定の保存だけで、Actionsの実行成功を報告しない。

## 開発の停止

ユーザーが全体停止を指示した場合、時間設定を無効にしてcronを削除する。
稼働中の制御プログラムは、次回の設定確認で安全停止する。
即時停止の依頼では、利用可能な既存連携のジョブ取消し機能を確認する。
取消し後の最終保存は保証しない。保存済みコミットを確認して報告する。
全体停止から、各企画の開発許可を勝手に取り消さない。
企画だけの停止依頼では、ユーザーの指示に従って対象の開発許可を変更する。

## 開発の再開

再開は、ユーザーが対象企画を明示した場合だけ行う。
最新の企画書が `allowed` で、状態が構想または開発中であることを確認する。
対象の実行状態、所有者、非公開設定、企画ID、リポジトリID、Issueを照合する。
閉じたIssueや完了企画を勝手に再開しない。
再開処理は、実行用コードの `resume --idea-id <id>` と同じ順序で行う。

1. 実行状態を `blocked`、理由を `resume_in_progress` として保存する。
2. 対象Issueの `agent:blocked`・`agent:review` だけを外す。
3. 対象Issueへ `agent:ready` を追加する。
4. 実行状態を `paused` とし、試行回数を0へ戻す。

他のラベルと企画書・議事録・メモは保持する。
部分的な更新失敗では、再開完了を報告しない。
ユーザーの開発許可の指示と、実行状態の再開操作を混同しない。

## 状況確認

実行管理用リポジトリの `state/projects.json` を取得する。
対象企画の開発ブランチ、最終コミット、Issue、PRを取得する。
利用可能な場合、Actionsの現在のジョブ状態も取得する。
保存済みの `running` だけを根拠に、現在も稼働中とは断定しない。

ユーザーへ、対象企画・保存済み状態・更新日時・残課題・確認済みリンクを示す。
`review` はユーザーの確認待ちであり、企画全体の完了とは限らない。
`blocked` は、認証・仕様・費用などの対応待ちである。
`paused` は、保存済み成果から次回に再開する状態である。
認証成功と認証情報の更新・書き戻し成功は区別する。
費用の確認データが古い場合、制御プログラムは起動しない。
費用データは所有者による確認も必要であり、完全自動検証とは報告しない。
